아이템의 키가 너무 다양하므로
ux측면에서 상태를 저장하는 기능 필요성을 느낌
(공고 사이트 특성상 이력서 지원을 위해 검색기록을 여러번 왔다갔다 해야함)

1. url에 키값을 부여하기로 결정

어차피 특정번호를 db에 조회하여 호출하는식이니 직접 하드코딩을 하여
규칙을 만들어보기로함

-> 실패
1) 특정번호를 사용하는건 맞지만 번호가 겹치는 경우가 있었음
2) 그래서 a01, a02 식으로 문자열을 포함하여 구현 성공
3) 하지만 대분류수가 늘어남에 따라 하드코딩 경우의수가 너무 많아져서 빠르게 접기로 결심
  


2. 경우의수를 만들기가 힘들다면 자동생성 기능의 도움을 받기로 결정

찾아보니 JSON 형태로 관리하고, 이를 Base64로 인코딩하는 방법이 존재했음

-> 실패

1) Base64로 인코딩하는 방식은 훌륭했음 (
   ㄱ. 따로 하드코딩할필요없이 자체생성 (기존방식은 분류가 추가될때마다 안겹치는 경우의수의 코드를 생각해내야했음)
   ㄴ. 자체생성이 되다보니 코드길이면에서도 훌륭 (최초 생성코드와 아이템 클릭시 변환하게끔만 해주면 되었음)

2) 하지만 선택되는 아이템이 많아질수록 URL이 길어지고 나중에 가선 URL제한이 생겨서 막힐것만 같았음

3) URL 길이를 무시한다고 쳐도 Base64로 인코딩하면 데이터의 크기가 약 33% 증가한다고 하니 현재구현방식에는 쓸수 없다고 판단


3.  JSON 직렬화 방식으로 섹션에 저장

-> 성공


{
    "categories": [
        {
            "category": "대분류1",
            "subName": "중분류1",
            "value": "소분류값1"
        },
        {
            "category": "대분류1",
            "subName": "중분류2",
            "value": "소분류값2"
        },
        {
            "category": "대분류2",
            "subName": "중분류1",
            "value": "소분류값3"
        }
    ]
}
섹션에는 해당 방식으로 저장될것이며 url도 깔끔하고 원하는대로 구현에 성공함

단점 : 현재방식에서는 데이터가 많이 소모될 가능성은 적으나 섹션에 많은 데이터를 담는건 브라우저데이터에 영향을 끼치니
        분류의수가 증가할시에 다른 방법을 모색해야함 현재는 사이트 구현정도에서는 사용가능
