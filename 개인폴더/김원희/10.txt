멤버십 페이지

최초 진입시 섹션에 저장된 사업주 로그인 정보를 조회하여
맴버넘버로 조회된 사업장 갯수를 패치요청을 보내고
반환 받은 결과를 에이싱크 어웨이트 방식으로 구현함

1. 사업주로그인정보가 없으면 비회원으로 판단

2. 사업장이 1개일 경우 바로 렌더링 시작 (ID: test99@test.com PW: pass01!

3. 사업장이 여러개 일 경우 먼저 섹션에 선택했던 기록을 조회후
   섹션 정보가 없으면 모달창을 뛰움

4. 최초진입(섹션에정보가없음) 일 경우 모달창을 벗어나지 못함
    (사업장을 반드시 선택하여 사업장 번호를 얻어야 하기 때문)

5. 사용자가 사업장을 선택하면 해당 정보를 섹션에 저장하고 렌더링 시작

6. 이후 페이지 재진입시에도 섹션정보를 읽어와 모달창을 뛰우지 않음
    (비교는 맴버넘버로 비교함 사업장번호로 조회하는건 무결성이 되지 않으므로 )

7. 렌더링 방식은 사용자 멤버십 유/무 판단하여 등급/잔여일에 맞게 화면이 변경됨

8. 화면 구현방식은 기본적으로 시작하기 버튼이 잔여일로 나오게끔 되어있으나
   상품중에서도 업그레이드 방식을 표현하고 싶었기에 골드 <-> 플레만 승계방식으로 설계함
   (승계방식이란 하위레벨 정보를 그대로 계승하며 상위레벨 존재시 하위레벨 선택불가)


결제 페이지

파이널 시작하고 처음 맡은 파트였기 때문에
이때까지만 해도 리엑트를 충분히 작업 할수 있을꺼라 생각해서
리엑트 수업시간에 배운것을 복습 하고자
서버 요청은 ResponseEntity, JS는 마치 여러개를 호출하는것처럼 구현해보려고 했음
그래서 하나의 페이지 형태라 새로고침시 멤버십 페이지로 넘어가게 됨

이말은 처음 사업자선택 당시 최초의 패치요청으로 화면 렌더링이 유지 되고있다는 뜻이고
사용자가 뭔가를 선택할때마다 요청을 보내는식이면 비교적 구현이 쉬웠을것이라 생각이 드나
JS만을 이용하여 서버요청없이 계속 다른 결과를 내야하니 구현이 조금 힘들었음
경우의수가 많은 부분이라 생각이 들어서 하나의 패치요청으로만 끝내보기로함

그래서 동적으로 변하는 영역마다 새로운 변수로 관리하게 했고
최종값을 전역변수로 선언하여 변화가 있을때마다 새롭게 담기는 형식으로 구현함

페이지 로직은 멤버십 페이지에서 가져온값을 전역변수로 선언하고
각 화면 영역 부분에서 해당값을 알맞게 가공하여 렌더링한뒤
var로 선언된 전역변수 배열에 담아서 포트원 결제서버 및 결제 결과를 실제서버로 요청하는 방식
DOMContentLoaded,click,change,input,keydown(엔터를방지) 사용됨

각 영역마다 조건에 따라 다르게 표현되어야 했기 때문에 상당히 까다로웠음

1. 멤버십페이지에서 선택한 아이템의 데이터벨류와 기존멤버십 데이터를 가져옴
2. 선택한아이템을 최초상품으로 렌더링
3. 이후 상품형식에 따라 개월/일수로 나눠짐
4. 사용자가 기존멤버십이 있을경우 상세정보에 기존정보 렌더링 없을경우 기본정보만
5. 위에서 선택한 상품형식에 따라 new,기간연장,upgrade 렌더링 후 남은기간 계산 (개월은 무조건 30일)
6. 선택한 상품들을 모은 배열에 각 상품을 삽입후 이용권x상품수 = 가격 형식으로 개별 가격과 전체가격을 렌더링
7. 포트원서버로 결제번호,주문번호,상품번호를 보냄
8. 해당 정보로 결제를 진행후 결제서버는 리스폰결과를 반환
9. 7번의 주문번호를 실제서버로 보내는게 아니라 반환받은 주문번호를 서버로 보냄 (보안을 위해서)
10. 사후검증을 위하여 실제서버에서 반환받은 리스폰데이터들과 DB데이터 조회
11. 해당 데이터로 토큰을 생성하여 포트원 서버로 보냄
12. 결제당시 클라이언트쪽에서 보낸 주문번호와 토큰을 생성하며 실제서버에서 보낸 주문번호가 일치하는지 확인
13. 검증이 완료되면 결제에 대한 정보를 실제서버 DB에 삽입

14. DB 삽입시 많은 로직이 필요했음
    1) 1번의 결제에서 이루어진 결제번호는 동일해야한다.
    2) 신규멤버십일 경우 인설트지만 기존상품일 경우 업데이트가 되어야한다.
    3) 하지만 반환받은 결과로는 서버에서는 기존/신규를 구별하지 못한다. (멤버십번호가 없으므로)
    4) 상품중에선 신규/기존도 있지만 기존에 업그레이드 형식도 존재한다.

15. 일단 반환받은 결과를 컨트롤러에서 빌드를 이용하여 해당하는 정보들로만 이루어진 새로운 맵으로 재조립
16. 1단계로는 결제정보와 결제정보 해소테이블 데이터를 삽입 이후 셀렉키로 결제번호를 지정하여 set,get을 이용함
     2단계로는 기존멤버십을 경우 배열의 길이만큼 반복하여 업데이트 이떄도 셀렉키로 결제번호를 지정하여 해소테이블에 연결
     3단계로는 신규멤버십 생성인데 신규는 멤버십 번호가 없으므로 클라이언트쪽 요청단계전에 신규를 일 경우 카운트를 해서
                   카운트 수 만큼 반복하게 함
     4단계로는 골드,플레에 대한 작업인데 서버에서는 골드가 있어도 멤버십번호가 없었으므로 플레를 신규로 처리함
                   그래서 DB조회결과가 골드,플레 공존 할경우 골드멤버십을 N 으로 업데이트 하는 로직 처리가 필요함

17. 사용자에게 결과를 반환
